# 0.8.DRAFT: Plan Development

- **Status**: Draft, not an RFC yet (2026-10-25)
- **Target**: SCS 0.8.0
- **Builds on**: RFC 0002 (Agent-Mediated SCS), section 9, as amended 2026-10-25

This is the full draft of an RFC 0002 amendment that was cut back for 0.7. 0.7 keeps only the
reservations the scaffold and validator need: `plan/`, `test-plan/`, and `qa/` are reserved
directories in every workspace, and `plan`, `test-plan`, and `qa` are reserved bundle names.
Everything below is the remainder, kept as the starting point for 0.8. The proposed text is
written against RFC 0002's sections.

## Idea

A Domain repository becomes the repository for a plan and the artifacts derived from it, not
only for context. The plan (architecture, component model, data model, interfaces, roadmap)
is the single source. SCDs, the test plan, and the QA plan are derived from it, and each
derived item traces back to the plan section it came from. Application repos stay the place
where the work gets built.

## Proposed text

### Summary

Append to the Domain repository description: "...holding the Domain workspace and the
workspaces of the Projects that run under it, with room in each workspace for the plan the
context derives from."

### Guide-level: One repository per Domain

Add after "Below a Project are the applications it covers...":

> Each workspace also has room for a plan: the architecture, component model, data model, and
> roadmap that the context derives from, along with the test and QA plans derived from the
> same source. Keeping the plan beside its context means the source and what was derived from
> it are versioned together, and the application repos stay the place where the work gets
> built.

### Section 1: Scope

Add a row to the operations table:

| Area | Operations |
|---|---|
| Plan | Create and edit files in a workspace's plan directories (section 9) at the user's request |

0.8 extends this row with generation from the plan and validation of plan content.

### Section 9: Domain repositories

Application repositories "MUST NOT be used to author it or its plan."

Layout, Project workspace:

```
projects/infusion-pump-fw/
├── .scs/config
├── intake.yaml
├── plan/                  # the plan the context derives from
├── test-plan/             # test plan derived from plan/
├── qa/                    # QA plan derived from plan/
├── bundles/
├── context/
├── sources/
└── dist/
```

**Plan directories.** `plan/`, `test-plan/`, and `qa/` hold a plan and the artifacts derived
from it, in every workspace, Domain and Project alike. Each is optional. The scaffold MAY
create them.

A plan differs from a source document (section 8). Source documents are external inputs kept
for reference, such as a quality manual or an SOP. A plan is authored and maintained in the
repository, and the workspace's other artifacts derive from it.

**Agent instructions.** The scaffold generates an agent instructions file stating that the
repository manages the plans and SCS context for one named Domain and its Projects, that work
in it is limited to maintaining those plans and their derived artifacts and to creating,
maintaining, validating, versioning, and compiling that context, and that application work
belongs elsewhere.

**Versioning.** Plan baselines are tagged `<workspace>/plan-v<version>`, which the 0.7
reservation of the bundle name `plan` keeps free of collisions.

### Alternative: A separate plan repository

The plan could live in its own repository, with the Domain repository holding only context.
That separates the source from what is derived from it: tracing an SCD item back to the plan
section it came from would cross repositories, and a plan change and the context changes it
causes could not be reviewed or tagged together. Rejected in favor of plan directories in each
workspace.

## To design in 0.8

- **Plan structure.** Keyed to the ontology. The sdlc ontology already reads as a plan's table
  of contents (`system-context`, `component-model`, `data-model`, `integration-map`,
  `infrastructure-definition`, `qa-procedures`, `validation-plan`, `success-criteria`).
- **Plan intake.** An intake that walks the plan structure, extending RFC 0002's "intake
  profiles per ontology" future possibility.
- **Derivation.** SCDs, test plans, and QA plans drafted from the plan, each item with a
  `derived_from` entry naming the plan section.
- **Plan baselines.** Each bundle version records the plan baseline it was derived from, so
  the chain plan version, bundle version, compiled artifact is traceable.
- **Stable vs. volatile layers.** Architecture, data model, interfaces, and quality standards
  are planned up front and become SCDs; feature detail is planned one roadmap increment ahead.
- **Re-derivation on change.** A plan change proposes the resulting SCD, test, and QA changes
  as a diff (extends RFC 0002's "re-intake on change").
- **Iteration.** Deriving artifacts exposes gaps in the plan; the loop plan, derive, fix plan,
  derive again is part of the workflow.

## Open questions

1. **Domain repository naming.** With the plan in the repository, `<domain-name>-context`
   describes only part of what it holds. Keep it, or change the convention (for example
   `<domain-name>-plan`)?
2. **Scope line.** RFC 0002 ends SCS at the versioned bundle. Does SCS define only the plan as
   a source type (structure and traceability), with the plan-development experience in a
   separate skill set or in SCP?
3. **Domain-level plans.** What a plan means at the Domain tier, where context is mostly
   organizational boundaries.
